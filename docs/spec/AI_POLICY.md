# AI_POLICY: rules for developing and reviewing with AI

[日本語](AI_POLICY.ja.md) · This English text is the main version; the Japanese version follows it, and where they differ, this text holds.

Status: **proposed (2026-11-14)**, waiting for a person's approval.

This document holds the rules for developing kirimaspice together with AI.

## Principles

- Most of kirimaspice's code is generated by AI tools. Humans are
  responsible for the specifications, the tests and the review. The README
  says so too.
- AI implements from the specifications: the model specifications (such as
  the BSIM4 manual), analytic solutions, and the documents under
  `docs/spec/`. When a change would contradict a specification, a human
  approves it first as a change to that specification.
- The shortcuts AI tends to take (rewriting expected values, adding
  branches for the shape of a symptom, and the like) are stopped by
  automatic checks where possible rather than left to human review.

## Marking commits

- A commit made with AI carries the trailer `Assisted-by: <tool>:<model and
  version>` (for example `Assisted-by: Claude Code:claude-opus-5-5`).
- `Signed-off-by:` is not used: the project does not run the DCO.
- `Co-Authored-By` is not used for AI.

## What humans hold

Humans decide the following; AI only proposes.

- The specifications (`docs/spec/`)
- The expected values of tests, and the list of tests allowed to fail
  (`tests/known_failures.txt`)
- Adding or removing a dependency, and installing a tool
- CI policy
- Text that is published

## Rules that protect expected values

- A change that alters, removes or loosens an expected value of an existing
  test goes in a commit separate from changes to the implementation. So
  does deleting or renaming a test, and adding a test to
  `tests/known_failures.txt`.
- New tests with their expected values may go in an implementation commit;
  a human checks their grounds.
- A change of an expected value states its reason and its grounds (the
  section of the model specification, the analytic solution, or the
  recorded version of a reference tool), and a human approves it.

## Record of human contributions

How the law treats what AI generates differs from country to country and
is not confirmed, so the history shows where a person's decisions and work
are.

- **Decisions:** the commit that records a person's approval of a
  specification or of an expected value carries the trailer
  `Approved-by: <name> <noreply address>`.
- **Review:** when a person has read a commit made with AI before it is
  pushed, the commit carries `Reviewed-by: <name> <noreply address>`. A
  commit without it has not been read line by line by a person.
- **What a person writes:** a commit that a person wrote without AI carries
  no `Assisted-by`. When a person and AI both wrote one, its message says
  which parts the person wrote.

## Clean room

- The AI that implements does not read source code under the GPL or LGPL
  (any version), such as Xyce, Qucs or Gnucap, and does not port it. KLU
  and BTF (LGPL) are used only through their public API. Files of ngspice
  are read only after their license is checked and found not to be GPL or
  LGPL.
- The behaviour of other tools is learned from their manuals and from
  running them; the version run is recorded.
- Tests are treated the same way: the reproducing code of other projects'
  issues and their test suites are not copied; the test is written anew
  from what the bug is.
- The text and figures of standards, papers and manuals are not copied:
  only references by section number and summaries in our own words.

## Contributions from outside

- For now, only specification proposals and issues are accepted from
  outside; code pull requests are not (`CONTRIBUTING.md`).
- When code pull requests are accepted, they must disclose AI use, and a
  human must understand the contents and take responsibility for them.

## What is not known

What has not been checked is written as "not confirmed", not filled in by
guessing. Version numbers are the ones actually looked up.
